Forward, backward, update

requires_grad, then the loop from micrograd

In the lecturePart 3 stopped as the training loop began. First the gradients are reset: setting them to None is “the same as setting it to 0 in PyTorch.” Then the backward pass: “And then loss.backward to populate those gradients.” “Once we have the gradients, we can do the parameter update”: every parameter’s data is nudged by minus the learning rate times its gradient. Repeat a few times, printing the loss. The first run stops with an error, because “we have to make sure that p.requires_grad is set to true in PyTorch.” With that, “this should just work”, and it does: “Okay, so we started off with loss of 17, and we’re decreasing it.”

for p in parameters:
  p.requires_grad = True

for _ in range(1000):
  # forward pass
  emb = C[X] # (32, 3, 2)
  h = torch.tanh(emb.view(-1, 6) @ W1 + b1) # (32, 100)
  logits = h @ W2 + b2 # (32, 27)
  loss = F.cross_entropy(logits, Y)
  # backward pass
  for p in parameters:
    p.grad = None
  loss.backward()
  # update
  for p in parameters:
    p.data += -0.1 * p.grad
print(loss.item())

As built in the lecture, on the 32 examples from five names. The notebook keeps only the later version with minibatches (move 3).

Nothing here is new: it is micrograd’s loop, now running over five tensors instead of a list of Values. Three details carry over. Gradients add up in PyTorch, so they are cleared before every backward pass; None and zero do the same job. The update goes through p.data so it isn’t itself tracked as part of the graph. And PyTorch only tracks what you ask it to: a tensor made by torch.randn has no gradient until requires_grad is switched on.

Watch forForget requires_grad and loss.backward() stops with “element 0 of tensors does not require grad and does not have a grad_fn” (PyTorch 2.15). Nothing in the forward pass needed a gradient, so there is no graph to go back through. Set it once, after the parameters are made, and before the loop.

Overfitting one batch

3,481 parameters, 32 examples, and a floor above zero

In the lectureRun it longer: “if we just run for 1,000 times, we get a very, very low loss”. That’s easy “because we’re only overfitting 32 examples”: “we have 3,400 parameters, and only 32 examples.” “So we’re doing what’s called overfitting a single batch of the data”. But “Now we’re not able to achieve exactly zero.” To see why, take the maximum of the logits along dimension 1. “In PyTorch, max reports both the actual values that take on the maximum number, but also the indices of these”. The indices are mostly the labels, but not everywhere: in the very first example, “the predicted index is 19, but the label is five.” That example’s context is dot dot dot, and in these five names dot dot dot is followed by e, o, a, i and s: “E, O, A, or S are all possible outcomes in a training set for the exact same input.” So the loss can’t reach zero, but “we’re getting very close in the cases where there’s a unique input for a unique output.”

Output from running the lecture’s seeded network for 1,000 steps at 0.1 (exercise 1).

With the seed from part 3, this reproduces the lecture to the index: 19 is s, where the label is 5, e. Of the 32 rows, 28 have the label as their most likely character; the four misses are all “...”, with labels e, o, a and i. The network has learned that “...” is followed by one of five letters and gives each about a fifth (e 0.199, o 0.194, a 0.202, i 0.180, s 0.223), so which one comes out on top is close to a coin toss. In fact it flips: at learning rate 0.1 the top pick for “...” swaps between i and s on every single step, and step 1,000 lands on s. The loss ends at 0.2561, just above the floor of 5 × ln 5 / 32 = 0.2515 that part 3 worked out.

Why bother? Overfitting a tiny batch is the cheapest test that the whole pipeline can learn at all. If the network can’t memorise 32 examples with 3,481 parameters, the bug is in the code, not the data.

3

Minibatches

All 228,146 examples are slow; 32 at a time are not

In the lectureBack to the dataset: drop the five-name limit and the prints, and “we now had 228,000 examples instead of just 32.” Re-initialise and train. The loss comes down, but “it takes quite a bit of time for every single iteration”: “we’re doing way too much work forwarding and backwarding 220,000 examples.” In practice people forward, backward and update on many small batches: “randomly select some portion of the dataset, and that’s a mini batch”. torch.randint makes the indices, 32 integers between 0 and the number of examples, and “I believe the size has to be a tuple in PyTorch.” Index both X and Y with them, and the embeddings are 32 by 3 by 2 again. “So okay, so it’s instant almost.” The price: “the quality of our gradient is lower”, so the direction is less reliable. It’s still good enough, and “it’s much better to have an approximate gradient and just make more steps than it is to evaluate the exact gradient and take fewer steps.” One more catch: the printed loss, hovering around 2.5, “is only the loss for that mini batch”. Evaluated on all of X and Y, “we’re at about 2.7 on the entire training set”, and then 2.6, 2.57 and 2.53 as training goes on.

ix = torch.randint(0, X.shape[0], (32,))
emb = C[X[ix]] # (32, 3, 2)
h = torch.tanh(emb.view(-1, 6) @ W1 + b1) # (32, 100)
logits = h @ W2 + b2 # (32, 27)
loss = F.cross_entropy(logits, Y[ix])

From the lecture (MIT licence). X is still every example here; the split comes in move 9.

How much cheaper? On my laptop, with one CPU thread, a step on all 228,146 examples takes about half a second, and a step on 32 takes about a quarter of a millisecond, some 2,000 times less (exercise 2). And the cheap steps lose little. After 1,000 of them the loss on every example is 2.71, after 2,000 it is 2.64, and after 5,000 2.57: the lecture’s 2.7, 2.6 and 2.57 almost exactly.

Why does a gradient from 32 examples work at all? The full loss is an average over all the examples, so its gradient is an average of their gradients. A random 32 gives a noisy estimate of that average, right on average and wrong in the details. Each step goes roughly downhill, and thousands of rough steps beat a handful of exact ones. The noise shows in the printed loss: over steps 900 to 1,000 it wandered between 2.24 and 3.29 while the true loss sat near 2.7. To know where you are, evaluate on everything, outside the loop.

Too slow, too fast

Bracket the rate by hand before you search

In the lecture“So one issue, of course, is we don’t know if we’re stepping too slow or too fast.” The 0.1 so far was a guess: “I just guessed it.” One way to find a reasonable rate starts by bracketing it. Reset the parameters, print the loss at every step, run 10 or 100 steps, and try rates. Very low, and “the loss is barely decreasing”. At 0.001, “we’re decreasing the loss, but like not very quickly”, which makes a good low end. At 1 the loss still falls, but “It goes up and down quite a bit”: a fast rate. At 10, “This is not working very well.” So the right rate is somewhere between 0.001 and 1.

(In the code the rate sits inside p.data += -lr * p.grad, so the lecture reads its tries out with the minus sign: “negative one”, “negative 10”. The rates are 1 and 10.)

Try it — too slow, too fast

My runs agree with the lecture’s bracket. The loss on every example starts at 19.51. After 100 steps it is 19.15 at 0.0001, 17.18 at 0.001, 3.75 at 0.1 and 3.34 at about 0.18, the best of the 21. At 1 it bounces and ends at 8.46. At 10 it ends at 64.66, far above where it started: the steps overshoot so badly that each one makes things worse.

5

A thousand rates, one per step

Space them by the exponent, and look for the valley

In the lectureNow search between the two with torch.linspace: 1,000 numbers between 0.001 and 1. “But it doesn’t really make sense to step between these linearly.” Instead, make 1,000 exponents from −3 to 0 and raise 10 to them. “And therefore we are spaced exponentially in this interval.” “So these are the candidate learning rates”. Reset, run 1,000 steps, and use the i-th rate on step i, so the rate starts at 0.001 and ends at 1. Track the rate used and the loss that resulted, and plot them. Against the rate, the loss barely moves at first, reaches a nice spot, then turns unstable. Against the exponent, the good one is “roughly in the valley here”. “So somewhere around negative one as the exponent of the learning rate is a pretty good setting.” 10 to the −1 is 0.1, so “point one was actually a fairly good learning rate”, the one already in use. “But that’s roughly how you would determine it.”

lre = torch.linspace(-3, 0, 1000)
lrs = 10**lre

lri = []
lossi = []
for i in range(1000):
  # ... minibatch, forward, backward as before ...
  lr = lrs[i]
  for p in parameters:
    p.data += -lr * p.grad
  lri.append(lre[i])
  lossi.append(loss.item())

plt.plot(lri, lossi)

From the lecture notebook (MIT licence); its final loop keeps these lines commented out.

Why the exponent? What matters about a learning rate is its ratio to another, not the difference. 0.002 is twice 0.001; 0.501 is the same as 0.5 for every practical purpose. Spacing by exponent gives every tenfold range the same number of tries. My sweep, from the same start on seeded minibatches, bottoms out at an exponent of −0.80, a rate of 0.16: close to part 3’s −0.75 and the lecture’s −1. The lecture keeps 0.1, a little on the safe side of the valley floor, and that is the usual choice: the bottom of a sweep is already close to where things start to go wrong.

Watch forThe sweep is a rough guide. The network is learning while the rate rises, so the early steps look bad partly because they are early, and the best rate drifts as training goes on. Use it to find the range, not the third decimal.

Elsewhere in these notesThe sweep’s curve, from my run on the training split: part 3, move 16. The learning rate in micrograd: topic 31, move 8.

Beyond the lectureLeslie N. Smith called this kind of run a “LR range test” in “Cyclical Learning Rates for Training Neural Networks” (2017): “run your model for several epochs while letting the learning rate increase linearly between low and high LR values. This test is enormously valuable whenever you are facing a new architecture or dataset.” Smith raised the rate linearly over several passes through the data and watched the accuracy; the lecture steps the exponent over 1,000 minibatches and watches the loss. The idea is the same: one short run, a rising rate, and a look at where training works.

6

Train, then decay

0.1 for 30,000 steps, then 0.01: past the bigram’s 2.45

In the lectureWith some confidence in 0.1, take out the tracking, crank up the iterations and reset. After 10,000 steps: “Okay, so we’re at 2.48 roughly.” After another 10,000, 2.46. Now “let’s do one learning rate decay”: “we’re going to take our learning rate and we’re going to 10x lower it”, because late in training it may pay to go slower. One more run at 0.1 first, which still makes a dent. By the way, “the bigram loss that we achieved last video was 2.45”, so “we’ve already surpassed the bigram model.” With the decay, about 2.3. “Obviously this is janky and not exactly how you would train it in production”, but that is roughly the routine: “You first find a decent learning rate using the approach that I showed you”, train with it for a while, and at the end “decay the learning rate by say a factor of 10” for a few more steps. 2.3 with these 3,400 parameters is a dramatic improvement on the bigram.

Look at where the decay’s gain comes from. Of the drop from 2.426 to 2.328, 0.092 arrives in the first 1,000 steps after the switch and only 0.006 in the next 9,000. At 0.1 the parameters are near the bottom of the valley but keep jumping across it, each step overshooting a little in some direction; the training loss can’t settle below the level of that jitter. A ten times smaller step lets them settle into the floor almost at once, and then there is little left to gain at that rate.

A lower loss can lie

Big enough networks memorise their training set

In the lecture“Now there’s something we have to be careful with.” Is the network better than the bigram because its loss, 2.3, is lower than 2.45? “Now that’s not exactly true.” This network is small, but networks can have 10,000, 100,000 or millions of parameters, and “as the capacity of the neural network grows, it becomes more and more capable of overfitting your training set.” The loss on the training data can go very low, down to zero, while “all that the model is doing is memorizing your training set verbatim.” Sample from such a model and you get training names back exactly: “You won’t get any new data.” And on names it was never shown, “the loss on those can be very high.”

So far every loss on these pages has been measured on the very names the model learned from. That only says how well it fits them. A language model for names is meant to make new ones, so the score that matters is on names it has never seen. A big enough network can score well on its training names by remembering them, and then it has learned nothing that carries over.

Part 1 saw this happen with counting tables. With five letters of context, a table scored about 1.74 on the names it counted and 2.33 on unseen ones, and 86% of the names it sampled were straight copies of training names. In this part’s runs, the final network trained on just 1,000 names reaches a training loss of 1.42, while its loss on unseen names is 3.65, worse than a uniform guess (move 10’s lab).

Three splits

80% to train, 10% to tune, 10% to test once

In the lecture“So the standard in the field is to split up your data set into three splits”: “the training split, the dev split or the validation split, and the test split”, typically “say 80% of your data set, this could be 10% and this 10% roughly.” The training split optimises the parameters by gradient descent, as so far. The dev split is for development: choosing the hyperparameters, such as the size of the hidden layer, the size of the embedding, or the strength of a regularisation not used yet. Try many variations and see which one works best on the validation split. The test split measures the model at the end, and only “very, very sparingly and very few times”, because “every single time you evaluate your test loss and you learn something from it, you are basically starting to also train on the test split.” Look too often and “you risk overfitting to it as well as you experiment on your model.”

Train · 80%25,626 names, 182,625 examples: gradient descent sets the parameters here
Dev · 10%3,203 names: choose the settings
Test · 10%3,204 names: once, at the end

Three sets for three kinds of decision. The parameters are chosen by gradient descent, which sees only the training set. The hyperparameters (sizes, learning rate, number of steps) are chosen by you, looking at dev scores; you are a slow optimiser, but an optimiser, so dev gets used up a little with every decision. The test set is never used to decide anything. That is the only reason its number can be trusted as the score on new names. “Dev” and “validation” are two names for the same split.

Beyond the lectureSimon Prince’s Understanding Deep Learning (MIT Press, 2023), section 8.5, gives the same reason for a third set. If hyperparameters were chosen on the test set, “this would admit the possibility that these hyperparameters just happen to work well for the test set but don’t generalize to further data. Instead, we introduce a third dataset known as a validation set.” Train each candidate on the training set, “select the model that worked best on the validation set and measure its performance on the test set.”

build_dataset

Shuffle the names once, then cut at 80% and 90%

In the lectureBack where the words became X and Y, the code becomes a function that “takes some list of words and builds the arrays X and Y for those words only.” Then “I am shuffling up all the words”, and n1 and n2 mark 80% and 90% of the way through the list, about 25,000 and 28,000 words. The first 25,000 or so make the training set, the next 3,000 or so the dev set, and the last 3,204 the test set, each built into its own X and Y. From now on the network trains only on Xtr and Ytr. “Training neural networks can take a while”: usually you launch a batch of jobs and wait, sometimes for days. “Luckily this is a very small network.” One slip on the way, “we accidentally used a learning rate that is way too low”, the decayed 0.01, so back up to 0.1.

Underfitting

Train and dev agree, so the network is too small

In the lectureEvaluate on the dev set: “So we’re getting about 2.3 on dev.” The network never trained on those examples, and yet the loss is pretty decent. On the whole training set it’s about the same: “the training and the dev loss are about equal”. “So we’re not overfitting.” “This model is not powerful enough to just be purely memorizing the data.” Instead “we are what’s called underfitting”: when train and dev losses are roughly equal, the network is typically very small, and “we expect to make performance improvements by scaling up the size of this neural net.”

My run: 30,000 steps at 0.1 and 10,000 at 0.01 on the training split give train 2.3329, dev 2.3340. A gap of a thousandth. Two numbers, two readings. If train is much lower than dev, the model is memorising: overfitting. If they are about equal and both still high, the model has room to spare: underfitting, and more capacity should help.

Beyond the lecturePrince’s book (section 8.3) names the two sides. Underfitting is bias, the model unable to describe the pattern, and the cure is capacity: “For neural networks, this means adding more hidden units and/or hidden layers.” Overfitting is variance, the fitted model chasing the noise in its particular training set, and the first cure is data: “adding training data almost always improves test performance.” Chapter 9 of the book covers the other cures, regularisation among them.

300 hidden neurons

A thick loss curve, and a slow start

In the lectureThe easiest way to scale up is the hidden layer: “So let’s do 300 neurons.” 300 biases, and 300 inputs into the output layer. “We now have 10,000 parameters instead of 3,000 parameters.” Keep stats again, the step number as well as the loss, train 30,000 steps at 0.1, and plot the loss against the step: “there’s quite a bit of thickness to this”, because “the mini batches create a little bit of noise in this.” On dev, “We are at 2.5.” Not optimised well yet, probably because it’s bigger: “It might take longer for this neural net to converge.” Perhaps the batch is so small that there’s too much noise, and “we may want to increase the batch size so that we have a bit more correct gradient”. Halving the learning rate gives 2.32. Another suspect: perhaps “the bottleneck of the network right now are these embeddings that are two-dimensional”, as “we’re just cramming way too many characters into just two dimensions”. Then 2.23: “So just by decreasing the learning rate, I was able to make quite a bit of progress.” Finally “we’re at 2.23 and 2.24”, not much better than before.

My run of this network: 10,281 parameters. After 30,000 steps at 0.1 its dev loss is 2.49, the lecture’s 2.5, while the 100-neuron network was at 2.40 by the same point: the bigger one starts slower. After 30,000 more at 0.05, dev 2.38; after 30,000 at 0.01, train 2.276 and dev 2.284 (exercise 5). Better than 2.33, but three times the parameters bought only 0.05, and train still equals dev: still underfitting. So the hidden layer wasn’t what held it back.

Ten numbers per character

11,897 parameters, no magic numbers, and the log of the loss

Saturated tanh

Most hidden outputs start at ±1, where no gradient gets through

Ahead in the next lecture · 12:59 to 40:40“fixing the saturated tanh”; “calculating the init scale: “Kaiming init””; “batch normalization”.

The hidden layer has the same problem. Each of its 200 neurons adds up 30 inputs times weights drawn at full size, so its input to tanh has a spread of about 5.5 (5.48 in my run). tanh flattens anything beyond about ±2.6 to within 0.01 of ±1, and 62% of the hidden outputs start there. That matters for learning: the backward pass through tanh multiplies by 1 − t², which is almost zero when t is ±1. Averaged over the layer at the start, 1 − t² is 0.148, so most of the gradient never reaches W1 and C.

Scale W1 by 0.2 and b1 by 0.01 as well as fixing W2, and after 200,000 steps the network reaches train 2.036 and dev 2.104; the next lecture’s log has 2.0356 and 2.1027. The 0.2 is hand-picked. The next lecture replaces it with a rule, “Kaiming init”: scale by a gain over the square root of the number of inputs, 5/3 for tanh. Then it adds batch normalisation, which keeps each layer’s inputs well scaled throughout training.

This also bears on move 15’s surprise. With 4 characters of context and 16 numbers each, W1 has 64 inputs per neuron, so more of tanh saturates: 76% at the start, against 72% with 3. Fix the scales with that rule (and W2 as in move 18), and the network with 4 characters reaches dev 2.041 while the one with 3 reaches 2.081. More context helps once the starting scales are right.

Beyond the lectureBoth ideas come from 2015 papers that the next lecture’s description links. Kaiming He and colleagues, “Delving Deep into Rectifiers”, worked out the scale that keeps signals the same size through many layers. Sergey Ioffe and Christian Szegedy, “Batch Normalization”, made each layer standardise its own inputs over the minibatch.
